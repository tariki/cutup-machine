## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌─────────────────────────┐
│ UI/クライアントレイヤー    │ ← 静的フロントエンド(ブラウザ)。/api/generate を呼ぶだけ
├─────────────────────────┤
│ APIレイヤー               │ ← Honoルーティング、レート制限、エラー変換
├─────────────────────────┤
│ ドメインレイヤー           │ ← 形態素解析・マーコフ連鎖構築/生成(ビジネスロジック)
└─────────────────────────┘
      (データレイヤーなし。永続化を行わない要件のため)
```

#### UI/クライアントレイヤー
- **責務**: テキスト入力・ファイルアップロードの受付、`/api/generate`の呼び出し、結果表示
- **許可される操作**: APIレイヤーの呼び出し(HTTP経由)
- **禁止される操作**: ドメインレイヤーのロジックをクライアント側に複製すること(例: マーコフ連鎖生成をブラウザ側で行わない。外部APIとして同じロジックが呼べることが要件のため、生成処理はサーバー側に一本化する)

#### APIレイヤー
- **責務**: HTTPリクエストの受付、レート制限、ドメインレイヤー(`RequestValidator`を含む)の呼び出しと、`ValidationError`/`RateLimitError`等の例外からHTTPレスポンスへの変換
- **許可される操作**: ドメインレイヤーの呼び出し
- **禁止される操作**: 入力バリデーション・形態素解析・連鎖構築などのビジネスロジックを直接実装すること(いずれもドメインレイヤーに委譲する)

#### ドメインレイヤー
- **責務**: 入力バリデーション(RequestValidator)、形態素解析(Tokenizer)、マーコフ連鎖の構築・生成(MarkovChainBuilder/MarkovGenerator)
- **許可される操作**: 外部ライブラリ(kuromoji、zod)の呼び出し
- **禁止される操作**: HonoのRequest/Response等、HTTPプロトコルへの依存(単体テストしやすい純粋なクラス/関数として実装する)

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| 入力テキスト・生成結果 | なし(リクエスト処理中のみメモリ上に保持) | - | PRDで生成結果を永続化しない方針が明示されているため |
| レート制限カウンタ | プロセス内メモリ | - | MVPでは単一プロセス構成を前提とする(複数インスタンス構成にする場合はRedis等の外部ストアへの置き換えが必要)。送信元IPごとのカウンタは直近のレート制限ウィンドウ(機能設計書を参照)を過ぎたエントリを定期的に破棄し、アクセスしてきた送信元IPが際限なくメモリに蓄積されないようにする |
| 運用メトリクス(リクエスト数・成否・エラー種別ごとの内訳・処理時間分布・セッションID単位のリクエスト回数) | アプリケーションログ(標準出力/ログファイル等) | 構造化ログ(JSON等) | PRDのKPI測定に必要な最小限の集計指標。プライマリKPIの「不正な入力によるエラーを除く」成功率算出にはエラー種別の内訳が、セカンダリKPIの「同一セッション内での平均生成回数」算出にはセッションID単位の集計が必要となる。元テキストや生成結果の内容、利用者を特定できる情報(IPアドレス等)は記録しない |

### バックアップ戦略

該当なし(永続化するデータを持たないため)。

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| `POST /api/generate`(元テキスト合計10万字以内) | 5秒以内 | 実装後に計測して確定させる仮の目標値(PRDのKPIを踏襲) |
| `POST /api/generate`(元テキスト合計10万字超〜上限の30万字以内) | 10秒以内 | 実装後に計測して確定させる仮の目標値(PRDのKPIを踏襲) |
| ページ初回表示 | 3秒以内 | 実装後に計測して確定させる仮の目標値(PRDのKPIを踏襲) |

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ | 目安512MB | kuromoji辞書の読み込み(数MB〜数十MB)と、1リクエストあたり最大30万字のテキスト処理を考慮した仮の目安。実測して見直す |
| CPU | 1 vCPUを想定 | 形態素解析・連鎖生成は1リクエスト内で完結する処理であり、複数プロセス・複数スレッドによる重い並列計算を必要としない。ただしNode.jsはシングルスレッドで動作するため、1リクエストの処理(最大10秒、パフォーマンス要件を参照)がイベントループを占有する間、同一プロセス内の他のリクエストの処理は待たされる点に注意(下記スケーラビリティ設計を参照) |
| ディスク | 数十MB | kuromoji辞書ファイルのみ。永続データは持たない |

## セキュリティアーキテクチャ

### データ保護

- **暗号化**: 永続化するデータがないため対象なし。通信経路の暗号化(HTTPS)はデプロイ環境(リバースプロキシ等)側で終端する想定
- **アクセス制御**: 生成結果やレート制限カウンタ等の永続ファイルは持たないためそれらのファイルパーミッション設計は不要。ただしkuromoji辞書ファイルはディスク上に永続的に配置されるため、デプロイ環境(コンテナ等)でアプリケーションの実行ユーザーが辞書ディレクトリへの読み取り権限を持つことを確認する
- **機密情報管理**: 現時点でAPIキー等の機密情報は扱わない。将来レート制限用に外部ストア(Redis等)を導入する場合、接続情報は環境変数で管理する

### 入力検証

- **バリデーション**: `RequestValidator`による件数・文字数・パラメータ範囲チェック(機能設計書を参照)。Honoのミドルウェアでリクエストボディサイズの上限も設定する
- **サニタイゼーション**: ファイルアップロードはWeb UI(ブラウザ)側で`accept=".txt"`により選択可能なファイルを絞り込み、`File.text()`でテキストとして読み込んだ上でAPIに送信する設計とした(実装時の判断)。そのためAPIサーバーが受け取るのは常に文字列(`texts: string[]`)であり、ファイルの拡張子・MIMEタイプ・バイナリ形式はサーバーに渡らない。したがって「サーバー側でのファイル形式検証」に相当する保護は、貼り付けテキストと同じ`RequestValidator`の文字数上限チェックによって代替される(不正なバイナリを選択されても、テキストとして解釈されるだけで実行や解析はされないため、貼り付けテキストと同一の脅威モデルとなる)。外部APIから直接ファイルアップロード相当のリクエスト(`multipart/form-data`等)を受け付ける設計に変更する場合は、拡張子・MIMEタイプのサーバー側再検証を別途実装する必要がある
- **クライアントIPの取得**: レート制限・運用メトリクスで用いる送信元IPは、デプロイ環境のリバースプロキシがHTTPS終端時に付与する`X-Forwarded-For`ヘッダーの最も信頼できる区間(リバースプロキシが上書き・追記する末尾の値)から取得する。リバースプロキシを経由しない直接アクセスを許可しない構成とし、クライアントが自由に設定できるヘッダー値をそのまま信用しない
- **エラーハンドリング**: 内部エラーの詳細(スタックトレース等)はレスポンスに含めず、サーバーログにのみ出力する。形態素解析・連鎖構築・生成処理中の想定外の例外は、リクエスト単位のtry-catchで捕捉して500として応答し、`uncaughtException`/`unhandledRejection`ハンドラでもログ出力のみを行いプロセスを維持する(PRDの信頼性要件「アプリ全体がクラッシュしない」に対応)。ただし、プロセスが応答不能になるような致命的な状態を検知した場合は、デプロイ環境(コンテナオーケストレータ等)による自動再起動に委ねる

## スケーラビリティ設計

### データ増加への対応

永続データを持たないため、データ量増加によるパフォーマンス劣化(いわゆる「データが溜まって遅くなる」問題)は発生しない。個々のリクエストのテキスト量上限(合計30万字)を超えるものはAPIレイヤーで拒否する。

### 同時リクエストへの対応

PRDのスケーラビリティ要件(「1利用者のリクエストが他の利用者の処理に影響しない」)に対し、MVPの単一プロセス・シングルスレッド構成では以下の制約がある:

- Node.jsはシングルスレッドで動作するため、形態素解析・マーコフ連鎖の構築・生成という同期的に重いCPU処理を行っている間、同一プロセスは他のリクエストのイベントループ処理を進められない。したがって、大きなテキスト(合計30万字に近い入力)を処理中の利用者がいると、同時にリクエストした他の利用者の応答が待たされる可能性がある
- MVPでは、上記を許容範囲内に収めるため、リクエストあたりのテキスト量上限(合計30万字)を設けることで1回の処理時間の上限(10秒、パフォーマンス要件を参照)を制限し、影響を最小化する
- リリース後の実測でこの影響が許容できない場合は、次のいずれかの対応を検討する:
  - CPU負荷の高い処理(形態素解析・連鎖構築・生成)をNode.jsの`worker_threads`に切り出し、メインのイベントループを塞がないようにする
  - プロセスを複数起動してロードバランスする(その場合、レート制限カウンタを外部ストア(Redis等)に置き換える必要がある。データ永続化戦略を参照)

### 機能拡張性

- **プラグインシステム**: MVPでは持たない
- **設定のカスタマイズ**: 生成パラメータ(`maxWords`/`chainLength`)はリクエスト単位で指定可能
- **API拡張性**: PRD Post-MVPの多言語対応に備え、`Tokenizer`を言語に依存しないインターフェースとして設計し、実装の差し替えで対応できるようにする。将来的に非互換な変更が必要な場合は`/api/v2/...`のようなパスプレフィックスによるバージョニングを検討する

## テスト戦略

### ユニットテスト
- **フレームワーク**: Vitest
- **対象**: `RequestValidator`、`Tokenizer`、`MarkovChainBuilder`、`MarkovGenerator`(機能設計書のテスト戦略を参照)
- **カバレッジ目標**: 80%(既存プロジェクトに`@vitest/coverage-v8`が導入済み)

### 統合テスト
- **方法**: Honoのテストユーティリティ(`app.request()`)を用いたHTTPリクエスト単位のテスト
- **対象**: `POST /api/generate`の正常系・異常系(バリデーションエラー、レート制限超過)

### E2Eテスト
- **ツール**: 未導入。MVPでは手動確認で代替し、必要性が高まった時点でPlaywright等の導入を検討する
- **シナリオ**: テキスト入力→生成→結果表示、ファイルアップロード→プレビュー→生成

## 技術的制約

### 環境要件
- **OS**: Node.js(v24系)が動作するLinux/macOS/Windows
- **最小メモリ**: 512MB程度(上記リソース使用量を参照、仮の目安)
- **必要ディスク容量**: 数十MB(kuromoji辞書含む)
- **必要な外部依存**: なし(ネイティブバイナリ・外部データベース不要)

### パフォーマンス制約
- 元テキスト合計30万字を超える入力はAPIレイヤーで拒否するため、それを超えるデータ量に対する性能は保証しない

### セキュリティ制約
- 認証機構を持たないため、送信元IP単位のレート制限のみが濫用対策となる。より強固な保護(CAPTCHA、APIキー方式など)が必要になった場合は別途検討する(現時点ではスコープ外)
